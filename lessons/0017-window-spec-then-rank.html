0. Where you are

You already: registered both views, filtered open + amount IS NOT NULL in SQL, inner-joined name, built Window.partitionBy("name").orderBy(col("amount").desc(), "order_id").

You then return the SQL frame. w is unused. Spark never ranks. Official Window is “utility functions for defining window” — a spec object. Ranking is row_number() applied with .over(w).

1. Same 3 lines as 07 ex8 / 08 ex2

# you already have `joined` (the spark.sql result) and `w`
joined.withColumn("rn", row_number().over(w))  # paint ranks
      .filter(col("rn") == 1)                  # keep top-1
      .select("order_id", "name", "amount")    # drop rn (checker columns)

row_number “returns a sequential number starting at 1 within a window partition” (docs). Ties are broken by your second orderBy key (smaller order_id).

2. Walk the toy rows

1         Alice  100     ← Alice closed 200 dropped

One row per name on this data — so rn == 1 keeps all three. The window is still required: the checker wants the pattern, and the docstring says ties → smaller order_id.

Expected: (1, Alice, 100), (2, Bob, 50), (4, Carol, 150).

2b. Why SQL-only also PASSes

The harness compares the output bag (column names + row tuples). It cannot see whether you called row_number. After open AND amount IS NOT NULL + inner join, this toy set already is those three rows. So returning the SQL frame green-lights ex6. filter(rn == 1) is a no-op here (every remaining name already has rn = 1).

If you stop at .withColumn("rn", …) and leave rn on the frame, the harness fails — extra column. select("order_id", "name", "amount") is what makes a painted frame match the checker, not the filter.
